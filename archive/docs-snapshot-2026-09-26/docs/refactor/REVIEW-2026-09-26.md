## Outstanding findings

### R1 — Comment request: document the best-effort per-part face target

Location: `libs/repairer.py:324–345`; final acceptance at
`libs/processor.py:225–228`.

`_decimate_to_target_and_fix` checks the decimator's failure status and
topology, but does not check whether the returned face count actually meets
`target_faces`. PyMeshFix's output is also accepted without a face-count
check. The owner accepts this behavior and does not want a model rejected
solely because post-decimation face counts differ from the requested target.
The original P2 enforcement finding is withdrawn; the remaining request is
to document this intent in a code comment.

Real reproduction using the default pipeline on the tests' four-face
tetrahedron, with `processor.process(mesh, 0)`:

- Initial decimation: disabled; four input faces retained.
- Alpha-wrap output: **705,504 faces**.
- Per-part decimation target: **4 faces**; actual result: **64,614 faces**.
- Final verdict: **PROCESS**.

An additional controlled probe supplied an oversized decimator result to
`processor.process(mesh, 2, part_steps=identity_steps)`: four output faces
were accepted as `PROCESS` despite a budget of two.

Requested change: add a comment beside the per-part decimation explaining
that `target_faces` is a best-effort reduction target, not a strict acceptance
limit. `fast_simplification` may return a different face count; that alone
must not reject the model. Keep the existing execution-failure and geometry
checks. Do not add a face-count rejection gate, another decimation pass, or
tests requiring exact target compliance.

The real tetrahedron result above is retained as evidence of a large
deviation, rather than characterized as a slight difference. It does not
override the owner's decision to request documentation instead of enforcement.

### R2 — P2: shared logs do not uniquely identify source files

Location: `tools/batch_repair.py:77`.

`source_name = os.path.basename(source_path)` gives different jobs such as
`model-a/base.stl` and `model-b/base.stl` the same identifier. Their events
interleave in the shared log, preventing reliable attribution of activity
or an unfinished step to its source.

Required correction: use a unique source identifier, such as the full path
or a path relative to the batch input root, on every event. Keep the field
safe for tab-delimited output. Verify two same-basename jobs remain distinct.

### R3 — P2: step logs omit part identity

Location: `libs/repairer.py:231–240`, `514–516`, and `543–547`.

The user identified this during the review follow-up. Part indices are
included in stored `StepResult.detail` through `detail_prefix`, but that
prefix is not included in live step-log events. Every shell repeats the
same source and step identifiers; nested scans also lack part identity.
Consequently the live log cannot identify which part is being wrapped,
decimated, repaired, or scanned.

Required correction: carry part identity through all per-part events,
including nested scans and start/end pairs. Proposed representation: a
dedicated `part` column containing `1/N`, `2/N`, etc., and `-` for whole-model
events. This column format is a review recommendation, not an already
implemented or user-approved schema. Verify a multi-part model's events
remain attributable when interleaved with another job.

## Clarified requirement: `--max-faces 0`

The user explicitly clarified:

> when the --max-faces is 0 we want to only disable first decimation, the one after alpha wrap should be executed anyway because it produces huge output

The current unconditional post-alpha-wrap per-part decimation is therefore
intentional. The initial concern that zero should disable both decimation
stages was withdrawn and is **not a bug finding**.

Clarify the CLI help in `tools/batch_repair.py` and the `processor.process`
docstring: zero disables only initial whole-model decimation. Post-alpha-wrap
decimation still targets each part's pre-wrap face count. R1 requests a
comment explaining that this target is best-effort.
